Modern CMS Architectures: From Monoliths to Headless and JAMstack

Tags

A Content Management System (CMS) lets someone who doesn't write code edit the articles, images and pages of a website. Over the last decade the architecture of these systems has changed fundamentally, and building the admin panel for this portfolio made me look closely at the different approaches.

1. The monolithic CMS: everything in one package

In classic systems such as WordPress, the database, the admin panel and the theme that renders pages all run inside the same application on the same server. Setup is easy and the plugin ecosystem is huge.

  • Pros: A ready-made panel, user management and thousands of plugins.
  • Cons: Content and presentation are tightly coupled, so reusing the same content in a mobile app is awkward. The server has to be patched and watched for vulnerabilities all the time.

2. The headless CMS: content as pure data

A headless CMS has no presentation layer. Content is served as JSON through an API, and a website, a mobile app or a smartwatch fetches it and renders it with its own interface. Strapi, Sanity and Contentful are well-known examples.

The core idea of headless: write the content once, show it everywhere.

3. JAMstack and static generation

With JAMstack (JavaScript, APIs and prebuilt Markup), pages are generated as HTML before deployment and served from a CDN. Because nothing is rendered on the server per request, sites load very fast and the attack surface shrinks. Dynamic needs such as forms, search or payments are handled by separate APIs.

4. This site's approach: a lightweight browser-based CMS

This portfolio has to run on serverless hosts such as GitHub Pages or Vercel, so I built a small three-layer setup:

  1. A single source of data: every project, article and photo lives as JSON in the content.js model.
  2. A shared rendering layer: the same render.js view functions generate static HTML at build time and re-render content in the browser, so the content is visible even with JavaScript turned off.
  3. Local saving: edits made in the admin panel are stored in localStorage, and the “download as content.js” button produces the file to publish.

This setup has an honest limit: localStorage belongs to one browser. A change made in the panel doesn't reach other visitors until the file is exported and the site is redeployed. A real multi-user system needs authentication and server-side storage.

Which architecture, when?

  • Personal portfolio or small project: a static site with JSON data, or a Git-based CMS, is enough.
  • Blog or company site with non-technical editors: a monolithic or managed headless CMS.
  • The same content on web, mobile and other channels: a headless CMS and API-first design.

Choosing an architecture is a question of need, not fashion. Asking who produces content, how often and for which channels points to the right structure on its own.

Micro-interactions and Glassmorphism in Modern UI/UX Design

Tags

Behind a user's feeling that an interface is “polished” there are usually small details nobody consciously notices: a button that sinks slightly when pressed, an input that glows when focused, a card that tilts to follow the mouse. These are called micro-interactions, and I used the idea in almost every element of this portfolio.

The four parts of a micro-interaction

Designer Dan Saffer describes micro-interactions with four components:

  1. Trigger: the event that starts it — a click, a hover or a change in data.
  2. Rules: what happens once it is triggered.
  3. Feedback: the moment the user sees, hears or feels the result.
  4. Loops and modes: how the interaction changes over time or in different states.

In this site's contact form, for example, the trigger is focusing a field, the rule is that the border turns into a coloured light, and the feedback is that the user instantly sees which field they are in.

Timing is everything

  • For small state changes, 100–300 ms is usually enough; anything longer feels slow.
  • Ease-out curves look natural because the object seems to “settle into place”.
  • Animating only transform and opacity lets the browser hand the work to the GPU and keeps motion smooth.

Glassmorphism: the frosted-glass effect

Glassmorphism is a visual language that creates depth by blurring the content behind semi-transparent surfaces. The basic CSS recipe is short: a translucent background, a thin light border and backdrop-filter: blur().

Glass only means something when there is colour or motion behind it; on a flat background it is just a grey box.

That's why this site places coloured light orbs and an animated network behind the glass. The effect has two costs, though:

  • Readability: as the background changes, so does text contrast. Text needs a dark enough layer beneath it, and WCAG contrast ratios should be checked.
  • Performance: the blur may be recomputed every frame. Keep the number of glass surfaces on screen low and the blur radius reasonable.

Don't forget accessibility

Some people are bothered by motion or get dizzy from it. The operating system's “reduce motion” setting can be read in CSS with prefers-reduced-motion. When it is on, this site stops the background animation, cards no longer tilt and the marquees stand still. A good micro-interaction also respects the user who doesn't want it.

In short, micro-interactions are the body language of an interface: in the right dose they quietly tell users what is happening; too much of them is just distraction.

Web Performance Optimization: From Core Web Vitals to 60 FPS

Tags

This portfolio has a constantly moving network animation in the background, frosted-glass cards and dozens of photos. Is a visually rich site doomed to be slow? No — but performance has to be considered from the start.

Core Web Vitals: a shared language for speed

Google evaluates user experience with three core metrics. The thresholds considered “good” are:

  • LCP (Largest Contentful Paint) ≤ 2.5 s: how long the largest image or text block takes to appear.
  • INP (Interaction to Next Paint) ≤ 200 ms: how quickly the page responds to clicks and key presses. It replaced FID in March 2024.
  • CLS (Cumulative Layout Shift) ≤ 0.1: unexpected movement of elements while the page loads.

Images: the biggest win

  1. Giving every <img> a width and height lets the browser reserve space up front and prevents CLS.
  2. Adding loading="lazy" to images below the fold makes the first load lighter.
  3. Giving the main image (such as the portrait on the home page) fetchpriority="high" improves LCP.
  4. Serving images close to their display size and in modern formats (WebP, AVIF) cuts file size dramatically.

Fonts

On this site, fonts are loaded as woff2 files from the project itself rather than an external service. The most important font is requested early with preload, and font-display: swap keeps text visible while fonts arrive.

Rules for smooth animation

  • Animate only transform and opacity; properties like width or top force the layout to be recalculated every frame.
  • Run JavaScript animation with requestAnimationFrame, not setInterval; the browser pauses it automatically when the tab is hidden.
  • Listen to scroll and mouse events as passive, and do the work once per frame rather than on every event.

Practical tips for canvas

For 60 FPS, each frame has to be drawn in roughly 16.7 ms. In the background network animation I took these measures:

  • The number of nodes is calculated from the screen area and capped; phones draw fewer nodes.
  • On high-density screens, the pixel ratio is capped at 1.75.
  • A cheap bounding-box check runs before computing the distance between two nodes, avoiding needless square roots.
  • When “reduce motion” is on, the animation draws a single frame and stops.

You can't improve what you don't measure: Lighthouse and the browser's Performance panel are far more honest than guesswork.

Performance isn't a final check; it is part of the design. Balancing visual richness with speed is one of the most valuable skills a front-end developer can have.

AI-Assisted Software Development: What Is Vibe Coding?

Tags

In February 2025, AI researcher Andrej Karpathy used the phrase “vibe coding” to describe a new way of writing software: the programmer explains what they want in plain language, a language model writes most of the code, and the human runs the result and steers by feel. The term quickly became one of the most talked-about ideas in software.

As a computer programming student, this concerns me directly. On one hand we are learning algorithms and syntax; on the other, tools that can do the same job in seconds get better every day. So how should we use them?

How does vibe coding work?

It is the classic “write, compile, debug” loop turned into a conversation:

  1. Describe the goal: “Write a Python script that averages the grades in a CSV file.”
  2. Run the generated code: The model gives you a draft and you run it.
  3. Give feedback: You paste the error message or the unexpected output back to the model.
  4. Repeat: The loop continues until the program does what you want.

Ideas and verification matter more than typing here. Whoever can describe the goal clearly gets the better result.

Where does it really help?

  • Quick prototypes: getting a working draft in a few hours to see whether an idea holds up.
  • Repetitive code: form validation, file reading, simple API calls, the patterns every project needs.
  • Learning: exploring an unfamiliar library through example code and asking “what does this line do?”
  • Small tools: one-off scripts that make your own work easier.

Traps to watch for

An AI can write wrong code in a very confident voice. The most common problems are:

  • Shipping code you don't understand: code accepted because it runs, without knowing its logic, becomes impossible to fix at the first bug.
  • Security holes: passwords hard-coded into the source and unchecked user input show up often.
  • Libraries that don't exist: a model sometimes invents a package or function name.
  • Missing tests: code that gave the right answer once can break on different input.
The AI can write the code, but responsibility for it always stays with the person who adds it to the project.

A healthy-use checklist for students

  • Read every generated line, and ask the model to explain anything you don't understand.
  • Try to solve the problem yourself first, then compare with the AI's solution.
  • Move in small steps: ask for one function at a time instead of a whole program.
  • Write at least one simple test for each important function, e.g. assert average([2, 4]) == 3.
  • Never paste personal data, passwords or API keys into the chat.
  • Follow your course rules: find out whether AI use is allowed for each assignment or exam.

Conclusion

Vibe coding doesn't end programming; it changes the programmer's role. A good developer is no longer only someone who types code, but someone who asks the right question, judges the output and thinks about the system as a whole. That makes learning the fundamentals more important than ever: only someone who knows the subject can catch the AI's mistakes.

Color Theory in Adobe Photoshop and Digital Design

Tags

Much of what makes a design feel “right” or “wrong” at first glance is colour. It was also what I spent the most time on in my Photoshop work: the charcoal colorization, the black-and-white contrast piece and the product poster. In this article I summarise the basics of colour theory and practical ways to apply them in Photoshop.

The colour wheel and three properties

In digital design it helps to think of a colour through three properties. The HSB model in Photoshop's colour picker shows exactly that:

  • Hue: the colour itself, red, yellow, blue… expressed as its angle on the wheel.
  • Saturation: how vivid or grey the colour is.
  • Brightness: how light or dark it is.

On screen, colours are defined in RGB; for print, in CMYK. Checking the colour mode before sending a poster to print prevents a colour that glows on screen from coming out dull on paper.

Harmony schemes

  • Complementary: colours opposite each other on the wheel (like blue and orange). The strongest contrast, ideal for emphasis.
  • Analogous: neighbouring colours (yellow, orange, red). Calm and unified.
  • Triadic: three evenly spaced colours. Energetic but hard to balance.
  • Monochromatic: lighter and darker values of one hue. A safe choice for minimal, elegant designs.

The 60-30-10 rule

A simple rule for distributing colour weight: about 60% of the area is the dominant colour, 30% the secondary colour and 10% the accent. In my product poster, the yellow background was dominant, the white tube secondary and the orange SPF label the accent, so the eye goes to the product first and then to the slogan.

Ways to control colour in Photoshop

  • Adjustment layers: Hue/Saturation, Color Balance and Curves change colour without destroying the original pixels. If you don't like the result, just delete the layer.
  • Blend modes: when colorizing a charcoal drawing, painting colour on a separate layer set to Color or Soft Light keeps the lines and shading intact.
  • Selective colour: turn the image grey with a Black & White adjustment layer, then erase the area you want in its mask, and that region stays in colour. That's how I made the player stand out in my black-and-white contrast project.
  • Gradient Map: maps the light and dark tones of a photo to colours you choose, creating a consistent mood.
  • Saved palettes: extracting a palette from a photo with a tool like Adobe Color and saving it to the Swatches panel keeps the same colours across the whole design.

Colour psychology and accessibility

Colours carry associations: yellow speaks of energy and sunshine, blue of trust and calm, red of passion and urgency. But readability comes before association. Without enough contrast between text and background, even the most beautiful palette fails. On the web, a contrast ratio of at least 4.5:1 is recommended for normal text. Conveying information through shape or text as well as colour also means thinking about colour-blind users.

A good palette has few colours, and every colour has a job.

Conclusion

Colour theory is less about memorising rules and more about making deliberate choices. Deciding the dominant, secondary and accent colours before you start, and making changes non-destructively with adjustment layers in Photoshop, saves time and makes the result look more professional.

Principles of Responsive Design in Modern Web Development

Tags

Today most visitors reach a website from a phone. The same page has to read comfortably on a 360-pixel screen and on a 1920-pixel monitor. Responsive design is how a single codebase adapts to every screen. Below are the principles I applied while redesigning this portfolio site.

1. Start with the viewport tag

Without this line, mobile browsers render the page at desktop width and shrink it:

<meta name="viewport" content="width=device-width, initial-scale=1">

2. Think mobile-first

Designing for the smallest screen first and adding features as it grows is easier than the reverse. A small screen forces you to decide what really matters. In CSS, that means writing the base styles and adding @media (min-width: …) blocks for larger screens.

3. Fluid grids: Grid and Flexbox

Work with proportions instead of fixed pixel widths. This line of CSS Grid adjusts the number of columns to the screen width on its own:

grid-template-columns: repeat(auto-fit, minmax(260px, 1fr));

Flexbox, with flex-wrap: wrap, moves items that don't fit to the next line. In many cases you don't even need a media query.

4. Fluid type with clamp()

To keep headings proportional on every screen, clamp() is very handy:

font-size: clamp(2rem, 5vw, 4rem);

This keeps the text at least 2rem and at most 4rem, growing with the screen width in between. For body text, keeping lines around 65–75 characters long makes reading easier.

5. Let content set the breakpoints

Place breakpoints where the design starts to break, not at device sizes like “iPhone width” or “tablet width”. Slowly narrow the browser window; the moment the layout gets cramped is the time to add a media query.

6. Responsive images

  • img { max-width: 100%; height: auto; } stops images from overflowing.
  • aspect-ratio and object-fit: cover crop photos of different sizes neatly into the same frame.
  • Setting width and height attributes prevents the page from jumping while images load.
  • loading="lazy" delays images below the fold until they're needed.
  • srcset sends smaller files to small screens and saves data.

7. Don't forget touch and accessibility

Phones have no mouse; buttons and links should be big enough to tap comfortably, about 44×44 pixels. For keyboard users the focus outline must stay visible, and text must have enough contrast against its background.

Responsive design isn't a feature, it's a requirement: visitors don't ask which device you'd like them to use.

8. Test on real devices

The device view in the browser's developer tools is a good start, but always open the page on a real phone too. Text size, tap targets and the feel of scrolling only become clear that way.

Conclusion

Fluid grids, type that scales with clamp(), breakpoints that come from the content and responsive images together make a site feel natural on every screen. This site's side menu turning into a top bar on phones and its cards dropping to a single column are results of the same principles.
